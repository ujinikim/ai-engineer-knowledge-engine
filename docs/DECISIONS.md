# Decisions

Decisions 001, 002, and the documentation-retention part of 006 describe the
original prototype. The active product now collects articles only.

## 001: Start With Documentation, Not News

Stable documentation is better for the MVP because it is easier to evaluate, easier to cite, and better for learning core RAG mechanics.

News/trend retrieval can be added later as a separate collection with recency-aware ranking and deduplication.

## 002: Use Curated URLs First

Broad crawling introduces scraping, deduplication, and scheduling problems too early. A curated list is enough to prove the full pipeline.

## 003: Expose Retrieval Internals

The UI should show chunks, scores, sources, latency, token usage, and cost. This makes the system useful for learning and stronger in interviews.

## 004: Keep Provider Interfaces Replaceable

Embedding and LLM services should hide provider-specific details so OpenAI can be replaced later with local embedding models or local LLMs.

## 005: Build A Knowledge Engine, Not A Chatbot

The primary interaction is a single question followed by ranked evidence, retrieval diagnostics, and an optional cited answer. The system does not maintain conversation history, user memory, or autonomus tool-use loops.

This keeps evaluation centered on retrieval quality and makes failures inspectable. Conversational behavior should only be added later if it serves a demonstrated workflow.

## 006: Pivot The Primary Product To Dated Developer Updates

The original documentation RAG proved ingestion, embeddings, retrieval, citations, and observability. The primary product is now a dashboard of recent AI developer-tool releases with RAG analysis over selected time windows.

Stable documentation remains a separate collection. This preserves the working foundation while aligning the interface and ingestion pipeline with the intended update-monitoring use case.

## 007: Start With Official Release Feeds

Official GitHub release feeds provide canonical URLs, timestamps, and authoritative text. They are preferable to broad news scraping for the first update MVP because freshness and deduplication can be measured reliably.

General publications require cross-source story clustering and a stronger source-quality policy, so they are deferred.

## 008: Keep Dashboard Ranking Deterministic

The feed is ranked from stored metadata and transparent scoring, not generated by an LLM. The LLM is only used after retrieval when a user asks for analysis.

## 009: Separate Generated Feed Copy From RAG Evidence

New and changed items receive a structured headline, summary, why-it-matters sentence, key points, and taxonomy metadata at ingestion time. These fields power the article feed. Question answering continues to retrieve original source chunks so generated summaries never become the sole evidence for another model.

## 010: Use A Controlled Multi-Axis Taxonomy

Each story has one primary engineering topic plus bounded event types, source type, maturity, and flexible entity tags. This avoids forcing research, releases, and tutorials into one overloaded category field while keeping filters predictable.

## 011: Prefer Source Quality Over Feed Volume

The source registry distinguishes first-party evidence from selected editorial synthesis. Official releases, changelogs, newsrooms, research, and engineering posts are the primary tier. Curated publications are admitted only when they consistently explain technically relevant developments and remain labeled as editorial analysis.

Popularity and community feeds are not treated as ordinary publications. They require dated signal snapshots, provenance, and story clustering so ranking changes and repeated announcements are represented honestly.

## 012: Use Explicit Adapters For HTML-Only Sources

Some high-quality publishers do not expose RSS or Atom. The collector supports those sources through configured listing-link patterns and article-content selectors. It does not perform broad crawling or autonomous browsing.
