# Retrieval Upgrades

## Implemented

### Hybrid Search

The default search mode is now `hybrid`.

Hybrid search combines:

- vector similarity from pgvector
- lexical keyword scoring over retrieved chunk text and titles

This helps exact-term questions such as:

```text
Show all documents mentioning streaming responses.
```

Tradeoff:

Hybrid search can over-favor sources that repeat the exact query terms often. Use source-balanced retrieval for cross-source comparison questions.

### Source-Balanced Retrieval

The frontend and API now support `retrieval_strategy: source_balanced`.

This runs retrieval per source and then merges results. It helps questions like:

```text
Compare memory, persistence, and conversation state across LangGraph and OpenAI.
```

Tradeoff:

Source-balanced retrieval can include lower-ranked chunks from some sources to preserve coverage.

### Retrieval Thresholds

`/ask` accepts `min_similarity`.

If the top score is below the threshold, the backend returns a warning and skips the LLM call.

### Context And Answer Budgets

The answer service now caps:

- context tokens sent to the LLM
- completion tokens generated by the LLM

This reduces worst-case latency and cost.

## Latency Finding

The slow path is the LLM call, not retrieval.

Recent profile:

```text
Avg total latency: 4796ms
Avg LLM latency: 4334ms
Avg embedding latency: 279ms
Avg retrieval latency: 157ms
Avg context tokens: 3145
Avg completion tokens: 280
Max total latency: 6752ms
```

Implication:

- pgvector retrieval is fast enough for the MVP.
- The UI waits for the full non-streaming LLM response.
- Longer context and longer answers increase response time.

Best next latency improvements:

1. Add streaming responses to improve perceived latency.
2. Lower default top-k for normal Q&A.
3. Keep source-balanced/high top-k for debugging and comparison questions.
4. Try a faster answer model if answer quality remains acceptable.
